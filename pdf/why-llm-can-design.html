この資料の前提

読み手は、Transformerが学習の末に「次に来るトークンを確率的に選ぶ」原理を理解しており、MCP・RAG・AIエージェント（推論はLLMに任せ、道具としてToolを用意する）・Agent Skillsの使い方と定義の仕方も知っている方を想定しています。そのうえで残る疑問はこれです。

問い 文章しか出せないはずのLLMが、なぜ人間が見て分かりやすい配置を考えられるのか。文章をどうやって「イメージ」に変換しているのか。

先に結論

  1. LLMは絵を描いていない。書いているのは「どこに・何を・どの大きさで置くか」を記したテキスト（コード）であり、画像にするのはレンダラ（PowerPoint、ブラウザなど）です。
  2. レイアウトは言語として学べる。HTML/CSS・SVG・スライドのXMLなど、見た目を記述したテキストが学習データに大量にあり、座標や大きさも「次トークン」として予測できます。
  3. 配置の整合は、文脈内の数値の参照と計算で取っている。スライド幅・余白・隣の要素の位置を注意機構で参照し、足し引きで矛盾のない値を出します。
  4. 「見やすさ」の知識は、学習データと事後学習、そしてスキルが補う。スキルは余白・文字サイズ・失敗例を明文化し、出力の確率分布を「人が見やすい側」へ寄せます。
  5. 仕上げは「AIの目」と検証ループ。画像をトークン列に変換して読めるマルチモーダルなモデルは、描画結果を見て、はみ出しや重なりを見つけて直せます。最後の確認は人間の目です。

1. 誤解をほどく

LLMは絵を描かず、「設計図」を書いている

文章からイメージへの変換は、LLMの中で一度に起きているわけではありません。

「LLMがスライドを作る」と聞くと、LLMが頭の中に絵を思い浮かべ、それを出力しているように感じます。しかし、Claude CodeがAgent Skills（pptxスキル）を使ってPowerPointを作るとき、LLMが出力しているのはテキストだけです。具体的には、スライド生成ライブラリ（pptxgenjs）を呼び出すJavaScriptのコードです。

下は前回の勉強会スライド1枚目で、実際に私が書いたコードの一部です。左右2枚のカードと矢印を置いています。

box(s, 0.5,  2.95, 4.05, 1.85, C.gray);                 // 左カード
s.addShape(RIGHT_ARROW, { x: 4.7, y: 3.65, w: 0.6, h: 0.45 }); // 矢印
box(s, 5.45, 2.95, 4.05, 1.85, C.tint, { line: C.accent }); // 右カード
s.addText("今日の「スキル」＝ Agent Skills", { x: 5.7, y: 3.1, w: 3.7, fontSize: 16, bold: true });
引数の読み方（単位はインチ。スライドは幅10×高さ5.625、位置は左上の角を基準に測る）
box(s, x, y, w, h, 色, 枠)角丸の四角を描く自作の補助関数。s＝描くスライド、x, y＝左端・上端からの距離、w, h＝幅・高さ、C.grayなど＝塗り色、{ line: … }＝枠線の色

1. 誤解をほどく

レイアウトは「言語」である

人類は、見た目をテキストで記述する方法を数十年かけて大量に作ってきました。

Webページ、図、スライド、文書の多くは、内部では見た目を記述するテキストとして保存されています。同じ「青い角丸の箱に文字を置く」も、形式ごとに次のように書けます。

形式同じ内容の記述例
SVG<rect x="40" y="20" width="200" height="80" rx="8" fill="#eaf2f5"/>
HTML/CSS<div style="width:200px;padding:16px;border-radius:8px;background:#eaf2f5">
PowerPoint（XML）<a:off x="457200" y="182880"/><a:ext cx="1828800" .../>（単位EMU）
pptxgenjsaddShape(ROUNDED_RECTANGLE, { x: 0.5, y: 0.2, w: 2, h: 0.8 })

学習データには「コード」と「その見た目の説明」がセットで含まれる

Web上には、コードとその見た目についての言葉が一緒に載った文書が無数にあります。たとえば次のようなものです。

  • CSSのチュートリアル：「margin: 0 auto で中央寄せになります」
  • Q&Aサイト：「ボタンが右にはみ出します」→「box-sizing: border-box を指定してください」
  • デザインの解説記事：「見出しは本文の2倍以上の大きさにすると階層が伝わる」
  • GitHub上の大量のHTML・SVG・スライド生成コードと、そのREADMEやコメント

次トークン予測の学習は、これらの文書で「この記述の次には何が来るか」を当てる訓練です。損失を下げるには、コードの数値が見た目とどう対応するか（大きいwは幅が広い、yが増えると下に移る、など）を内部に表現しておくのが有利です。こうしてモデルは、絵を一度も「見ずに」、見た目と記述の対応関係を獲得します。

有名な例：テキストだけのモデルがユニコーンを描いた 2023年の論文 “Sparks of Artificial General Intelligence” では、画像を扱わない段階のGPT-4に「TikZ（LaTeXの作図言語）でユニコーンを描いて」と依頼しました。GPT-4は、胴体・脚・角を図形の組み合わせとして記述するコードを出力しました。さらに角を消したコードを渡すと、正しい位置に角を描き足しています。完璧な絵ではありませんが、言葉だけの学習から「形と配置」の知識が生まれることを示した例として広く知られています。

1. 誤解をほどく

ラベルのないデータから、どうやって「良し悪し」を学ぶのか

学習データの1件1件に「このデザインは見やすい／見にくい」という採点が付いているわけではありません。

Web上のHTMLやスライドのコードには、それが画像として優れているかどうかの採点は付いていません。それでも良し悪しの区別が身につくのは、主に次の4つの理由によります。

① 良し悪しは「周りの文章」に書かれている

評価はデータに付与されていなくても、多くの場合データの中に書かれています。Q&Aサイトの質問と回答、デザインの添削記事、「改善前・改善後」の比較記事などがその例です。

次トークン予測は、コードとその周りの評価語（「読みにくい」「すっきりした」）をまとめて予測する訓練です。その結果、モデルの中に評価語を条件にしたコードの分布ができます。依頼文に「見やすく」と書くと、「見やすい」という言葉と一緒に現れやすかったコードの確率が上がります。

P( コード | 「見やすい表を作って」 )　≠　P( コード )

② たくさん採用されたものほど確率が高くなる

公式テンプレートや広く使われるデザイン部品（CSSフレームワークなど）は、プロが作ったものが何万ものサイトに複製されます。一方、駄作は散発的で、パターンもばらばらです。そのため、確率の高い領域には「多くの人に採用され続けた無難な良作」が集まります。採用の多さが、自然な投票の役割を果たしているのです。ただし、これは「無難」であって「最良」ではありません（p.7）。

③ 学習前にデータを選別している

一般に開発元は、学習の前に重複や低品質な文書を取り除きます。Claudeの具体的な選別方法は公開されていませんが、壊れたページや意味をなさない文書は減らされていると考えるのが自然です。

④ 足りない分を、人の選好とスキルで補う

①〜③で得られるのは「だいたい良い」までです。その先は、人間の選好による調整（p.7のRLHF）と、明示的な基準を与えるスキル（p.8）が補います。

2. 座標はどう決まるか

次トークン予測で「4.05」が選ばれる理由

座標の数値も、ほかの単語と同じく確率分布から選ばれる「次トークン」です。

GPT-2で学んだ通り、LLMは位置tの隠れ状態 ht から、次のトークンの確率を出します。

P(xt+1 | x1, …, xt) = softmax( Wout ht )

スライドのコードを書いている途中で box(s, 5.45, 2.95, まで来たとき、次の候補には数値トークンが並びます。どの数値が高い確率になるかを決めるのは、注意機構が参照する文脈です。

整合性は「文脈内の計算」で取れている

前回のスライドの値を足し算すると、配置の意図が読み取れます。

0.5（左余白）+ 4.05（左カード）+ 0.9（矢印を含む間隔）+ 4.05（右カード）= 9.5　⇒　右余白 10 − 9.5 = 0.5

左右の余白が等しく、カード幅も等しいので、人間の目には「バランスが取れている」と映ります。LLMはこのような関係を、すでに書いた数値（文脈）を注意機構で参照し、内部で足し引きした結果として次の数値に反映します。大規模モデルが数桁の加減算を内部で行えることは広く確認されており、レイアウトの座標計算はその応用です。

直感的なまとめ 「スライド幅10インチ」「余白0.5インチ」「左カードの幅4.05」という制約が文脈にそろうと、次の数値の分布は矛盾のない値の近くに鋭く集中します。LLMは画面を見て配置を決めているのではなく、数値の制約を満たす続きを書いているのです。

2. 座標はどう決まるか

LLMの内部には「空間」が表現されている

言葉だけで学習したモデルの中に、空間の構造がほぼそのまま現れるという研究があります。

Gurnee & Tegmark（2024, ICLR）は、Llama-2（7B〜70B）に地名（「東京」「パリ」など）を入力し、各層の隠れ状態 h から実際の緯度・経度を当てられるかを調べました。使ったのは、最も単純な線形の読み出し（リッジ回帰）です。

( 緯度, 経度 ) ≈ W h + b

結果、隠れ状態からかなりの精度で座標を読み出せました。この表現はモデルの前半の層で形成され、大きいモデルほど精度が高くなっています。さらに、非線形の読み出しを使っても精度はほとんど上がりませんでした。これは、空間がベクトル空間の中のほぼ「平らな方向」として埋め込まれていることを意味します。

レイアウトとの関係（ここは類推です）

この研究が直接示しているのは地理と時間の表現であり、「スライドのレイアウト」を調べたものではありません。ただし、次の点は合理的な類推として言えます。

  • テキストだけの学習でも、「上・下・左・右・隣・内側」のような空間的な関係を、ベクトルの方向として持てる。
  • 座標の数値トークンと「右側」「中央」「はみ出し」といった言葉が、同じ空間の近い方向に結びつく。だからこそ「右に寄せて」という指示を、xの値を増やす操作に翻訳できる。
ここまでの理解 LLMは「絵」を持っていません。代わりに空間関係を表すベクトルと、数値で整合を取る能力を持っています。この2つがあれば、見た目を記述するコードを矛盾なく書けます。

3. 「見やすさ」の知識

「良いデザイン」の知識はどこから来るのか

配置を矛盾なく書けることと、人が見て分かりやすいことは別の能力です。

ページ5の能力があれば、要素どうしが重ならず、余白もそろった配置は作れます。しかし「この内容なら左右の比較にする」「見出しは36pt以上にする」といった判断には、人間の視覚と理解についての知識が必要です。この知識は主に3つの経路から来ています。

経路何が入るか例
① 事前学習デザインの教科書、UIガイドライン、プレゼン指南、良い例・悪い例の議論「1スライド1メッセージ」「近接・整列・反復・対比」（デザインの4原則）
② 事後学習人間が「良い」と評価した出力に報酬を与える学習（RLHFなど）読みやすく整った回答や成果物が選ばれやすくなる
③ その場の指示プロンプトやスキルに書かれた規則・例・禁止事項「余白は0.5インチ以上」「タイトル下に線を引かない」
注：RLHF（Reinforcement Learning from Human Feedback、人間のフィードバックによる強化学習）
①同じ依頼に対するモデルの出力を複数並べ、人間がより良いほうを選ぶ。②その選択の記録から、出力の良さを点数にする「報酬モデル」を学習する。③LLMを、報酬モデルの点数が高くなる方向へ調整する。Anthropicは人間の評価に加えて、明文化した原則に沿ってAIが評価する手法（Constitutional AI）も使っています。なお、この評価で描画したスライドの見た目まで採点しているかどうかは公開されていません。

① だけでは「平均的なスライド」になりやすい

事前学習で得た分布は、世の中のスライドやWebページの平均的な姿を反映しています。そのため、何も指示しないと、よく見かける無難な構成（白地に箇条書き、青系の配色、タイトル下の飾り線など）が高い確率で出てきます。いわゆる「AIっぽいスライド」の多くは、この平均への引き寄せで説明できます。

ポイント 「見やすさ」は、LLMが自分の目で確かめて身につけたものではありません。人間が言葉で書き残したデザインの知見を、確率分布として取り込んだものです。そのため、知見を言葉で明示的に与える（スキル）と、出力の質は大きく変わります。

3. 「見やすさ」の知識

スキルは何をしているのか

スキルは「デザインの経験知」と「確かめるための道具」をLLMの文脈に差し込みます。

確率の言葉で書くと、スキルの効果は条件付けです。スキル本文 S が文脈に入ることで、同じ依頼 q でも出力 y の分布が変わります。

P( y | q )　→　P( y | q, S )

今回使ったpptxスキル（Anthropic公式）の SKILL.md には、たとえば次のような内容が書かれています（要約・抜粋）。

① 数値で書かれたデザイン規則

  • 余白は最低0.5インチ、要素間は0.3〜0.5インチ
  • タイトル36〜44pt、本文14〜16pt
  • 1色を主役（6〜7割）に、補助1〜2色＋差し色1色
  • どのスライドにも視覚要素（図・アイコン・図形）を入れる

② 失敗例（禁止事項）

  • タイトル下の飾り線、端の色帯を使わない
  • 本文を中央揃えにしない
  • 同じレイアウトを繰り返さない

③ 道具の落とし穴

  • キャンバスは幅10インチ×高さ5.625インチ
  • 色の指定に「#」を付けるとファイルが壊れる
  • テキストボックスには内側の余白がある

④ 検証の手順とスクリプト

  • PDFに変換し画像にして、1枚ずつ目視確認する
  • 確認項目：はみ出し、重なり、余白不足、低コントラスト
  • validate.py：ファイル構造の検査

①はページ7の「平均への引き寄せ」を打ち消す働きをします。数値で規則が書かれていると、ページ5で説明した「文脈内の数値を参照して整合を取る」能力がそのまま効きます。②は、事前学習の分布が特に起こしやすい失敗を名指しで潰しています。

なぜ「毎回プロンプトに書く」のでなくスキルなのか スキルは、普段は名前と説明（description）だけが文脈に置かれ、関係する依頼が来たときに本文が読み込まれます（段階的な読み込み）。そのため、こうした細かい経験知を大量に用意しておいても、文脈を圧迫しません。仕組みとしてはRAGに近いですが、検索するのはモデル自身であり、手順と道具（スクリプト）をひとまとめにして渡せる点が違います。
ここまでの理解 「配置を整合させる力」（ページ5〜6）に、「人が見やすい配置の規則」（スキル①②）が加わると、多くの場合は整った資料になります。ただし、まだ実際の見た目を確かめていません。それを担うのが次の「目」です。

4. LLMの「目」

画像もトークン列にすれば、Transformerで読める

マルチモーダルなLLMは、画像を「単語のような断片」に切り分けて入力しています。

テキストは単語（トークン）に分けてベクトルにします。ViT（Vision Transformer, 2020）は、画像についても同じことをしました。画像を P×P ピクセルの小さな正方形（パッチ）に切り、各パッチを1つのトークンとして扱います。

パッチ数　N = ( H / P ) × ( W / P )　　例：336×336画像、P = 14 → 24 × 24 = 576トークン

各パッチ（14×14×RGB = 588個の数値）を線形変換でベクトルにし、位置埋め込みを足してTransformerに入れます。GPT-2の「トークン埋め込み＋位置埋め込み」と同じ構造です。

画像と言葉を同じ空間にそろえる：CLIP

画像のベクトルが言葉と「話が通じる」ためには、両者を同じ意味空間にそろえる必要があります。CLIP（2021）は、約4億組の画像と説明文を使い、対応する組の類似度を高め、対応しない組の類似度を下げる学習（対照学習）を行いました。

類似度 = cos( f画像(画像), g文(説明文) )　→　正しい組で最大化、誤った組で最小化

LLaVA（2023）は、CLIPの画像エンコーダの出力 Z を学習可能な行列 W で単語埋め込みの次元に写し（H = WZ）、テキストと並べてLLMに入力しました。こうしてLLMは画像について質問に答えられるようになります。

4. LLMの「目」

作る → 描く → 見る → 直す、の検証ループ

ご存じのエージェントの原理（推論はLLM、道具はTool）が、そのまま資料作成にも当てはまります。

なぜループが必要か：コードからは見えない問題がある

ページ5の数値計算で分かるのは、図形の位置関係までです。次のような問題は、実際に描画しないと分かりません。

  • 文字の実際の幅：同じ14ptでも、フォントや文字の種類（全角・半角）によって幅が違い、折り返しの位置が変わる
  • フォントの置き換え：指定したフォントが環境にないと別のフォントで表示され、幅が変わる
  • 全体の印象：余白の偏り、窮屈さ、色のコントラスト不足など、数値の上では正しくても見ると不自然な点（どう判定するかは次ページ）

pptxスキルが「描画した画像を、先入観なしに見る（できれば別のエージェントで）」と指示しているのはこのためです。コードを書いた本人は「意図した通りになっているはず」と読んでしまうので、画像という別の入力経路で確かめさせています。

4. LLMの「目」

AIの目は「不自然さ」をどう判定しているのか

ここでいう「目」はAI（マルチモーダルLLM）自身の目です。人間の目は最後の確認役です。

この資料での実例：私はChromiumで各ページを画像にして読み込み（p.9の仕組みで画像トークンになります）、図5のラベルの不具合に気づきました。根拠は3つです。①コードとの照合：「意図のある」という灰色の文字を置いたはずの位置に、画像では濃い青しか見えなかった。②画像からの印象：背景とほぼ同じ明るさの細い文字は、縮小とパッチ化で特徴が弱くなる。③典型例の知識：「濃い色の上に灰色の文字」は低コントラストの定番の失敗。つまり、画像だけで判定したわけではありません。

注意：「AIが読める」≠「人が読みやすい」 ピクセル値は正確なので、人には埋もれて見える文字をAIが読めてしまうことがあります（逆もあります）。そのため、問うべきは「自分が読めるか」ではなく「人が見たら読みにくいと言うか」です。さらに確実なのは数値で測ることです。Webアクセシビリティの基準（WCAG）では、文字と背景の明るさの比（コントラスト比）が本文で4.5 : 1以上と定められています。計算すると、修正前は1.08 : 1（明るさがほぼ同じ）、修正後は5.67 : 1でした。この基準は人間の視覚の研究に基づくため、AIが読めるかどうかに左右されません。

判定を支える3つの仕組み

仕組み中身
① 探す項目を言葉でもらうスキルの確認項目（はみ出し・重なり・余白不足・低コントラスト）が「どこを見るか」を決める。画像と説明文の組から学んだ「見た目」と「言葉」の対応で、該当箇所を探す。
② 「よくある姿」からのずれを感じ取る不自然な文を「確率の低い文」と感じ取るのと同じ理屈。学習した「整ったページの典型」からのずれに、「窮屈」「読みにくい」といった言葉を当てはめる。
③ 「人間ならどう評するか」を予測する人間の知覚を測るのではなく、人間の批評や選好の学習（p.7）をもとに人が何と言うかを予測する。基準そのものは人間から借りている。
限界と、その補い方
  • 細かな寸法や色の差は見誤りうる → 測れるものは機械で測る（コントラスト比など）。
  • 見た目の好みには個人差がある → 最終判断は人間の目で行う。

5. 実例

前回のスライド作成で、実際に起きたこと

勉強会スライドの作成では、図7のループの②③（描画してAIの目で見る）が欠けていました。

状況

pptxスキルは、PDF変換（LibreOffice）と画像化（pdftoppm）でスライドを目視確認するよう指示しています。しかし、このDev Containersにはどちらも入っておらず、外部からのインストールも当時の規則（CLAUDE.md）で禁止されていました。そこで私は、目を使わずに次の代わりの方法で品質を担保しようとしました。

本来の手順実際に行ったこと確かめられなかったこと
描画した画像で、はみ出しを確認文字幅を計算で見積もる（14ptの全角1文字 ≈ 0.19インチ → 幅4インチに約20文字）Meiryo UIでの実際の幅、折り返しの位置
画像で全体のバランスを見る座標の足し算で、余白と対称性を確認見たときの窮屈さ、余白の偏り
validate.pyでの構造検査標準ライブラリでXMLの整合性を確認PowerPoint固有の制約
別のエージェントによる目視確認別のエージェントに文字だけを読ませて内容を確認視覚面の問題全般

見積もりの式

全角文字の幅はおおむね文字サイズと同じなので、次のように見積もれます（1pt = 1/72インチ）。

文字数 ≈ 幅[インチ] ÷ ( サイズ[pt] ÷ 72 )　　例：4.0 ÷ (14 ÷ 72) ≈ 20.6

この見積もりで「21文字の箇条書きは2行に折り返す。3項目で約5行になるので、高さ1.65インチにぎりぎり収まる」と判断し、本文を13ptに下げました。数値の推論としては筋が通っていますが、実際に収まったかどうかは、PowerPointで開いた人間が見るまで分かりません。そのため、納品時に「見た目の確認はできていない」とお伝えしました。

この実例から分かること
  • ページ5〜8の能力（座標の整合、デザイン規則）だけでも、ほぼ整った資料は作れる。
  • しかし最後の品質（文字の収まり、見た目の印象）は、描画して見ることでしか保証できない。
  • LLMが「見やすい資料を作れる」のは、LLM単体の力というより、LLM＋スキル＋レンダラ＋AIの目（最後に人の目）という仕組み全体の力である。

6. 対比

画像生成AI（拡散モデル）は本当に「描いている」

「文章をイメージに変換する」と聞いて思い浮かぶもう一つの技術は、仕組みがまったく違います。

Stable Diffusionなどの画像生成AIは、コードではなくピクセルを直接作ります。考え方の基本は「ノイズを少しずつ取り除く」です。

どうやって学び、どうやって描くのか（概念）

  1. 壊す練習：大量の写真に、わざと砂嵐（ノイズ）を少しずつ混ぜていきます。写真には「青い丸」のような説明文が添えられています。
  2. 直す練習：砂嵐の混ざった写真を見て「どんな砂嵐が混ざったか」を当て、取り除く練習を、説明文を手がかりにしながら何億回も繰り返します。
  3. 描く：完全な砂嵐から出発し、「青い丸」という言葉を手がかりに少しずつ砂嵐を取り除きます。最後に、元はどこにもなかった「青い丸の絵」が現れます。
たとえ 彫刻家が石の塊から余分な部分を削って像を彫り出すように、砂嵐から「余分なもの」を少しずつ削って絵を浮かび上がらせます。どこを削るかの判断に、言葉（説明文）を使います。言葉と絵をつなぐ役は、p.9で紹介したCLIPのような仕組みが担っています。
LLM＋コード（スライド作成）拡散モデル（画像生成）
出力設計図のテキスト（座標・文字列）ピクセル
文字の正確さ正確（文字列をそのまま指定）崩れやすい（形として描くため）
後からの修正数値を1つ変えれば済む作り直しになりやすい
得意なこと図表、整列、構造のある資料写真風・イラスト・質感
使い分けの理由 スライドのような資料では「文字が正確」「後から直せる」「整列している」ことが最も大事です。そのため、Agent Skillsでは拡散モデルではなくLLMがコードを書く方式が使われています。写真やイラストが必要なら、画像生成を「Tool」として呼び出し、その結果をスライドに配置する、という組み合わせが自然です。

まとめ

全体像：「見やすい資料」は仕組み全体で作られる

最初の問いへの答え

LLMは文章をイメージに直接変換していません。見た目を記述するテキスト（座標・大きさ・文字列）を、次トークン予測で書いています。それが整って見えるのは、①レイアウト言語と空間関係を学習で獲得し、②文脈内の数値を参照して整合を取り、③スキルが人間のデザイン知見で分布を絞り、④描画した結果を画像トークンとして読んで直すからです。

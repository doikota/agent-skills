# 無影響確認テストの技術基準

このファイルは、無影響確認テストのスキル（`SKILL.md`）が「どうやって行うか」を定める。何を満たすべきか（分類、合否の条件、役割）はガイドライン（`references/guideline.md`）に従う。食い違う場合は、ガイドラインを優先する。

ここに示すツールやコマンドは代表例である。対象アプリがすでに使っているツールがあれば、それを優先する。

## 1. 置き場所と名前

### 1.1 テスト資源を置くディレクトリ

レポートと一覧は、対象アプリのテスト資源を置くディレクトリの下の `patch-regression-reports/` に置く。テスト資源を置くディレクトリは、対象アプリの既存の構成から判断し、ユーザーに示して確認を得る。決めた場所は、設定ファイル（`auto-settings.md`）にも記録する。

| 言語 | よくある場所の例 |
|---|---|
| Java（Maven・Gradle） | `src/test/resources/` |
| Python | `tests/` |
| TypeScript | `test/`・`tests/`・`__tests__/` |
| C# | テストプロジェクトのフォルダ（例: `<アプリ名>.Tests/`） |

`patch-regression-reports/` の中には、次のファイルを置く。

| ファイル | 内容 |
|---|---|
| `call-sites.md` | 呼び出し箇所の一覧 |
| `flaky-tests.md` | 不安定なテストの一覧 |
| `auto-settings.md` | 対話なしでの実行の設定ファイル |
| `urgent-*.md`・`readiness-*.md`・`planned-*.md` | 無影響確認テスト実施レポート（「1.2：レポートのファイル名」） |

### 1.2 レポートのファイル名

| 場面 | ファイル名 |
|---|---|
| 至急対応 | `urgent-<CVE 番号>-<日時>.md`。複数の CVE をまとめて扱う場合は `urgent-<CVE 番号>_<CVE 番号>-<日時>.md` |
| 平時の恒久準備 | `readiness-<日時>.md` |
| 計画的な点検 | `planned-<日時>.md` |

- `<日時>` は、レポートを出力する日時を `YYYYMMDD-HHmmss` の形式で書く（例: `readiness-20261114-153045.md`）。
- Windows でファイル名に使えない `:` は使わない。

### 1.3 スキルが作る Issue のタイトル

きっかけの Issue がないためにスキルが Issue を作る場合は、次のタイトルにする。

| 場面 | タイトル |
|---|---|
| 平時の恒久準備 | `[無影響確認] 平時の恒久準備 <日時>` |
| 計画的な点検 | `[無影響確認] 計画的な点検 PR #<PR 番号>` |

本文には、場面、対象の PR（あれば）、レポートのファイルの場所を書く。

## 2. Issue と PR へのコメント

- コメントの投稿には `gh issue comment <番号> --body-file <ファイル>` と `gh pr comment <番号> --body-file <ファイル>` を使う。本文は一時ファイルに書いてから渡す（コマンドの引数に長い本文を直接書かない）。
- **文字数の上限。** GitHub のコメントの本文は 65,536 文字までである。レポートがこれを超える場合は、章の区切りで分割し、各コメントの先頭に `（1/2）` のように通し番号を付けて、順に投稿する。
- **PR へのリンク。** PR には、Issue に投稿したコメントの URL を 1〜2 行で書く（例: `無影響確認テスト実施レポート: <コメントの URL>`）。
- **承認の確認。** PR のレビューの状態は `gh pr view <番号> --json reviews` で読む。状態が `APPROVED` のレビューと、その投稿者を使う。

## 4. シグネチャの変更の確かめ方

| 言語 | 確かめ方 |
|---|---|
| Java・C# | パッチを当てた状態でビルドし、コンパイルエラーが出るかで確かめる |
| Python・TypeScript | 呼び出し箇所を通る既存のテストを実行して確かめる。型チェック（mypy・tsc など）が設定されていれば、あわせて実行する |

## 5. 確認観点ごとの確かめ方

ガイドライン「5章：確認観点チェックリスト」の観点ごとに、次の方法で確かめる。

| 確認観点 | 項目 | 確かめ方 |
|---|---|---|
| V1 | 起動とデプロイ | C1 ビルド・C2 起動スモークテスト |
| V2 | 間接依存の変化 | C1 の依存ツリーの比較 |
| V3 | 脆弱性の修正 | C4 脆弱性スキャン・C5 修正確認テスト |
| V4 | デフォルト設定の変更 | 呼び出し箇所の機能テスト。古い TLS の接続先、保存済みのデータ、外部参照を含む XML、SSO の戻りなど、既定値の変化で失敗しやすい入力を含める |
| V5 | 入力検証の厳格化 | 既存データ・境界値を使った機能テスト |
| V6 | 出力形式の変化 | 出力を比較する機能テスト・契約テスト |
| V7 | 例外とエラーの変化 | 異常系の機能テスト（例外の型、メッセージ、エラーコードを記録する） |
| V8 | ログと監視 | ログ出力を比較する機能テスト |
| V9 | 並行処理とリソース | ガイドライン「6章：性能劣化の判定基準」の性能確認 |
| V10 | 破壊的変更への対応 | 外部で修正されたソースコードを通り、パッチ前後で同じ結果を返すことを確かめるテスト |
| V11 | 実行環境・OS に固有の変化 | ガイドライン「3.3：確認範囲 3 向け環境確認の CI 自動化」の環境確認 |

## 6. 機能テスト

### 6.1 期待値を保存しないモード

至急対応と計画的な点検で、パッチ後の状態で追加したテストを試しに実行するとき（`SKILL.md`「8.1：実行の順番」の手順 1）は、期待値を新しく保存したり上書きしたりしないモードで実行する。

| ツール | 期待値を保存しない実行のしかた |
|---|---|
| Jest | `--ci` を付ける（スナップショットがなければ失敗する） |
| Vitest | 環境変数 `CI=true` を設定して実行する（スナップショットを書き込まず、欠けているものや合わないものがあれば失敗する）。`-u`（`--update`）は付けない。Vitest には `--ci` の引数はない |
| syrupy | `--snapshot-update` を付けない |
| ApprovalTests（Java・Python） | 受け取った結果（received）を承認済み（approved）にしない |
| Verify | 受け取った結果（`.received.`）を承認済み（`.verified.`）にしない。自動で受け入れる設定は使わない |

この手順で作られた記録ファイル（received など）は、比較の前に捨てる。

平時の恒久準備では、手順 1 で、追加したテストの期待値を新しく作る。このとき、追加したテストだけを対象に実行し、既存のテストの期待値（スナップショット）は上書きしない。

### 6.2 非決定的な値の伏せ方

時刻・乱数・ID など実行のたびに変わる値は、比較の前に伏せる。伏せ方は、テストごとに決めてテストコードに書く。

| ツール | 伏せ方の例 |
|---|---|
| Jest・Vitest | プロパティマッチャー（`expect.any(String)` など）を使う |
| syrupy | `matcher`（`path_type` など）で値の型だけを比べる |
| ApprovalTests | Scrubber で決まった文字列に置き換える |
| Verify | Scrubber（`ScrubInlineGuids` など）や `IgnoreMember` を使う |

- 時刻は、可能ならテストの中で固定する（時計を差し替える）。固定できない場合に伏せる。
- 伏せすぎると変化に気づけなくなる。伏せるのは、実行のたびに変わる値だけにする。

## 7. 不安定なテストの見つけ方

- 平時の恒久準備では、既存のテストを、コードを変えずに **5 回** 繰り返して実行する。結果が一定しないテストを、不安定なテストの候補とする。
- 至急対応と計画的な点検で、一覧にないテストが失敗した場合は、最大 **3 回** まで実行し直す（`SKILL.md`「8.4：失敗の切り分け」）。
- 候補を一覧（`flaky-tests.md`）に加えるかどうかは、ユーザーに確認する。一覧には、テストの名前、見つけた日、考えられる原因（時刻・乱数・実行順序・外部サービスなど）を書く。

## 8. パッチ前の状態の作業フォルダ

- 比較元ブランチを、`git worktree add` で別の作業フォルダに取り出す。現在の作業フォルダには触れない。
- 作業フォルダは、対象アプリのリポジトリの **外** に、スキルを実行するたびに新しく作る（例: `../<リポジトリ名>-patch-regression-worktrees/<YYYYMMDD-HHmmss>/`）。
- 作業が最後まで成功した場合は、`git worktree remove` で片付ける。
- 途中で失敗した場合や中断した場合は、原因を調べられるよう片付けずに残し、その場所をレポートに記録する。

## 9. 性能の測り方

ガイドライン「6章：性能劣化の判定基準」の測り方を、次のように行う。性能の測定は CI で行い、スキルは手元では測らない。

- **画面とサービス（バックエンド・Web フロントエンド・デスクトップアプリ）。** 準備運転（ウォームアップ）を 1 回してから **5 回** 測り、中央値で比べる。
- **バッチ処理。** ガイドライン「6.3：測り方」のとおり、制限時間内に収まるかで判定する（最大 3 回）。
- **ランナー。** パッチ前とパッチ後は、同じ種類のランナーで、同じ CI の実行の中で続けて測る。GitHub が用意するランナーは測定値がぶれやすい。厳密な比較が必要なアプリでは、自前のランナー（self-hosted runner）を検討する（用意は「チームで対応」）。
- **結果の読み取り。** `SKILL.md`「10章：承認の記録」では、CI の成果物やジョブの出力から、指標ごとのパッチ前・パッチ後の値を読み、ガイドライン「6.2：しきい値（初期値）」で判定する。
